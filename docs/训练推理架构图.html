总体架构总览

当前系统是统一多任务模型，不是三个独立模型。单张图像进入共享骨干后，同时产生真假分类、解释特征和伪造区域定位结果。 训练时通过 partial labels指同一个 batch 里，不同样本可拥有不同任务标签。代码里用 has_cls / has_loc / has_exp 表示样本能参与哪些任务。 支持“不是每张图都有三类标注”的现实数据条件；推理时则复用同一套模型参数输出三项结果。

这套框架为什么当前能跑通

它不是追求最复杂，而是优先保证“课程目标三条链路都通”。

  • 统一骨干让三项任务能共享视觉特征，避免三套模型各自为政。
  • partial labels 让分类集和多任务集可以自然拼接，不强迫数据满足完整三标注。
  • 解释任务先用检索式 baseline，降低训练复杂度与显存压力。
  • Stage A + Stage B 训练策略，有利于先稳住真假分类再联合优化。

这套框架当前最值得继续优化的地方

从当前实验结果看，优先级不是平均分配，而是有明显主次。

  • 分类：先解决未见生成器覆盖不足，特别是 glide / midjourney / wukong。
  • 解释：检索式 explanation 上限受限，适合引入线上大模型做增强。
  • 定位：监督链路已修通，但定位头还比较浅，后续可升级结构。
  • 系统层：可做本地模型 + 在线大模型的级联推理与离线蒸馏。

训练流程拆解

当前训练入口的核心不是“单一大一统数据集”，而是把分类训练集与 SynthScars 多任务集通过统一 batch 结构组织起来。 所有 loss 都在 compute_batch_loss 里按可用标注动态计算，这是训练逻辑的真正核心。

训练主流程

从数据构建到 best.pt 的路径

① 构建分类数据集

从多个分类根目录收集 train / val 样本，过滤坏图后构造真假分类集。

  • 支持多 root
  • 训练集固定 seed 随机截样

② 构建 SynthScars

读取图片、caption、polygon mask，并划分 train / val 索引。

  • 提供分类 + 解释 + 定位监督
  • 同时用于候选文本库构建

③ Stage A

只训练分类数据，让共享骨干先学会真假判别。

  • 重点看 Acc / AP
  • 先把分类能力热起来

④ Stage B

ConcatDataset(ImageNet, SynthScars) 做联合训练。

  • 三路 loss 同时参与
  • 用同一模型统一优化

⑤ 验证与保存

每轮验证后保存 latest.pt，并根据综合分更新 best.pt。

  • Stage A：Acc + AP
  • Stage B：分类 + 解释 + 定位综合

损失函数与任务掩码

真正决定训练逻辑的地方
total_loss = cls_weight * cls_loss + loc_weight * (bce_loss + dice_loss) + exp_weight * exp_loss 仅当对应标注存在时，才启用那一路损失。 这就是当前统一训练能兼容“部分标签数据”的关键。

当前训练上的真实短板

不是所有问题都该优先改结构

分类

生成器域偏移依旧是主矛盾。头部不是主要瓶颈，训练 fake 覆盖面才是。

解释

检索式解释天花板明显，适合引入线上大模型做“增强生成”或“教师蒸馏”。

定位

当前解码器偏浅，没有用 skip connection / FPN，导致细节恢复能力有限。

推理流程拆解

推理时当前系统仍然只走一次本地模型前向，然后把三路结果整理成最终输出。 其中 explanation 不是自由生成，而是“本地图像特征 → 候选文本库当前 explanation 并不是直接让模型生成句子，而是从预先准备好的 caption 集合里检索最接近的一条。检索”。这也是最适合后续接入线上大模型的切入点之一。

当前推理链路的优势

  • 本地一次前向即可得到三路结果，速度快，结构清晰。
  • 解释与定位可以直接绑定到同一张图像，便于展示。
  • 不依赖线上服务即可独立跑通，适合课程答辩与离线演示。

当前推理链路的不足

  • 解释文本过于受候选库限制，难以细腻描述复杂伪造痕迹。
  • 分类对未见生成器泛化不足，仅靠阈值微调帮助有限。
  • 定位结果已有起色，但缺少更强的结构化区域理解能力。

如何引入线上大模型来提高效果

如果目标是“在不彻底推翻现有本地多任务框架的前提下，尽快提高系统效果”，最合理的策略不是让线上大模型直接替代所有部分， 而是把它接到最能产生增益的位置：解释增强、难例复判、离线蒸馏、区域级多模态增强。

最推荐切入点
解释增强
第二优先级
难例复判
长期价值最高
离线蒸馏

方案 A：线上大模型只负责解释增强

推荐优先做

本地模型继续负责真假分类和定位，线上多模态大模型只根据 原图 + 预测 mask + fake_score + 检索到的 top-k caption 生成更自然、更细致的中文解释文本。

  • 对当前框架侵入最小，不会破坏已有训练链路。
  • 最直接改善解释质量、可读性和答辩展示效果。
  • 还能把 mask 区域与解释文字绑定起来，形成“哪里可疑、为什么可疑”的输出。
收益：高 改造成本：低 适合提升：BLEU / ROUGE-L / 展示效果

方案 B：本地先判，线上大模型只复判难例

推荐第二步

先让本地模型跑一遍，只有当 fake_score模型对 fake 类别的概率分数。分数越靠近阈值，说明模型越不确定，这类样本最适合交给线上大模型做二次判断。 接近阈值、或者 mask / explanation 与分类不一致时，才把样本送给线上多模态大模型做二级复判。

  • 最适合解决当前“未见生成器”导致的分类失败问题。
  • 只处理不确定样本，可以显著控制 API 成本与延迟。
  • 可以把线上模型输出当成辅助判断，而不是强行替代本地判定。
收益：中高 改造成本：中 适合提升：Acc / fake recall / 未见生成器鲁棒性

方案 C：把线上大模型当教师，离线蒸馏回本地模型

长期最值

用线上大模型给更多图像生成解释、软标签、难例判断，再把这些结果 蒸馏把更强模型或更复杂系统的知识，转移给当前较小或较快的本地模型。这里指用线上大模型产生的高质量输出，反过来训练本地模型。 回本地统一模型。这样线上服务主要用于 离线增强训练数据， 线上推理成本却不会持续累积。

  • 特别适合持续补充 glide、midjourney、wukong 等新生成器样本。
  • 可把线上模型的语言能力蒸馏到本地解释模块，或训练新的生成式 explanation head。
  • 对生产化最友好：效果来自大模型知识，但最终服务仍以本地模型为主。
收益：高 改造成本：中高 适合提升：全局泛化能力

方案 D：结合在线 grounding / segmentation 能力

谨慎选择

如果线上服务不仅是纯文本大模型，还带有 grounding / box / segmentation 能力，就可以让它为可疑区域提供更强的区域先验，再与本地 mask 做融合。

  • 这条路更像“在线视觉基础模型增强”，不是普通文本大模型单独完成的。
  • 对定位任务可能有帮助，但工程复杂度明显更高。
  • 如果只是普通 LLM，没有区域 grounding 能力，不建议直接指望它提升像素级定位。
收益：中 改造成本：高 适合提升：IoU / PixF1（前提是服务能力足够）

我对你这套框架的直接建议

  • 第一步：不要动本地训练主干，先让线上多模态大模型只做 explanation 增强。
  • 第二步：把线上大模型接成“难例二判器”，只接管 fake_score 边缘样本。
  • 第三步：把线上模型的输出缓存起来，做离线蒸馏，逐步减少线上依赖。
  • 第四步：如果以后真要冲定位指标，再评估 grounding / segmentation 型服务。

为什么不建议一上来就“全部交给线上大模型”

  • 成本高，且每张图都调用会带来明显延迟。
  • 输出风格不稳定，课程验收或演示时可复现性较差。
  • 纯文本大模型并不擅长像素级 mask，直接替代定位头往往不现实。
  • 你现有本地模型已经把三条链路打通，更好的策略是“增强它”，不是“推翻它”。

如果接线上大模型，最推荐的输入与输出格式

尽量结构化，方便程序接线

建议输入给线上大模型的信息

  • 原图（必要）
  • 本地模型输出的 fake_score 与当前 label
  • 预测 mask 或其可视化热图
  • 候选 explanation top-k 文本
  • 可疑区域裁剪图（按 mask 或 bbox 裁出）

建议要求线上大模型输出 JSON

  • final_label：real / fake
  • confidence：0~1
  • explanation_zh：中文解释
  • evidence_points：可疑点列表
  • need_human_review：是否建议人工复核

实施建议与落地顺序

如果你要继续把这个项目做得更像完整系统，而不仅是一个能跑通的 baseline，我建议按“低风险、高收益、可复用”的顺序推进。

中期关键

阶段 1：先提升展示与解释质量

保持本地模型不变，在推理后串接线上多模态大模型，输出更自然的中文 explanation。

  • 最容易出效果
  • 适合答辩展示
  • 不会影响已有训练流程

阶段 2：只让线上大模型接管难例

以 fake_score、top-k 解释一致性、mask 面积异常等规则触发二级复判。

  • 重点补未见生成器泛化
  • 控制延迟与成本
  • 可同时收集 teacher 数据

阶段 3：建立离线蒸馏闭环

把线上模型的高质量解释与复判结果沉淀成训练数据，再反哺本地统一模型。

  • 长期最划算
  • 减少线上依赖
  • 更接近可部署系统

工程侧必须注意的事

否则效果提升可能抵不过工程代价

调用策略

  • 不要所有图片都打线上接口，优先做条件触发。
  • 对同图重复请求要做缓存，避免浪费 API 配额。
  • 强制让大模型按 JSON 输出，减少解析不稳定。

系统稳定性

  • 线上接口超时或失败时，要能优雅回退到本地结果。
  • 不要让外部服务成为唯一真值来源。
  • 验收或展示时最好保留“纯本地模式”开关。

数据安全与成本

  • 确认图像是否允许发到外部服务。
  • 记录每次在线调用的收益，避免“加了大模型但性价比很低”。
  • 优先把线上能力沉淀为离线训练资产。

与当前项目的最佳结合点

  • 解释增强：接在 infer_multitask.py 后面。
  • 难例复判：接在 fake_score 判断后面。
  • 蒸馏闭环：接在新的离线数据标注脚本中。
总结一句：短期最值得做的是“本地模型负责判别与定位，线上大模型负责解释增强和难例复判”；长期最值得做的是“把线上大模型的知识蒸馏回本地统一模型”。
